## Contexte

Seule la CI applique l'infrastructure (NFR-01). Une fusion sur `develop` applique dev ; une release sur `main` applique prod après approbation manuelle. Le plan appliqué est celui qui a été revu (plan figé).

## User story

En tant qu'équipe OPS, je veux un apply GitOps par environnement, afin que l'état réel corresponde toujours au code fusionné et revu.

## Critères d'acceptation

```gherkin
# language: fr
Fonctionnalité: EN-73 — Apply GitOps

  Scénario: AC1 — develop vers dev
    Étant donné une fusion sur "develop" qui modifie "infra/"
    Quand le workflow s'exécute
    Alors les stacks foundation puis platform sont appliquées en dev avec le rôle apply de l'environnement "dev"

  Scénario: AC2 — main vers prod avec approbation
    Étant donné une fusion sur "main"
    Quand le workflow atteint l'environnement "prod"
    Alors il attend l'approbation d'un réviseur désigné avant l'apply

  Scénario: AC3 — Plan figé
    Étant donné un plan produit et revu dans le workflow
    Quand l'apply s'exécute
    Alors il applique exactement ce fichier de plan (chiffré)
    Et si l'état a changé entre-temps, l'apply échoue et un nouveau plan est demandé

  Scénario: AC4 — Concurrence
    Étant donné deux workflows sur le même environnement
    Quand ils démarrent
    Alors ils sont sérialisés (groupe de concurrence) et le verrou du state est respecté

  Scénario: AC5 — Traçabilité
    Étant donné un apply terminé
    Quand on consulte l'exécution
    Alors le commit, la PR et l'environnement sont visibles dans le résumé du job
```

## Exigences non fonctionnelles

- Aucun secret ni sortie sensible dans les logs du job.

## Notes techniques / décisions

- Ordre des stacks : foundation → platform ; le contrat passe par SSM `/smartcampus/<env>/<stack>/<key>`.
