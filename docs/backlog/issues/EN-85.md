## Contexte

Les parcours critiques traversent le front, Cognito, l'API et les données. Un test E2E Playwright les rejoue dans un navigateur réel sur dev.

## User story

En tant que QE, je veux des tests E2E des parcours critiques, afin de détecter les régressions visibles par les utilisateurs.

## Critères d'acceptation

```gherkin
# language: fr
Fonctionnalité: EN-85 — E2E Playwright

  Scénario: AC1 — Parcours étudiant
    Étant donné un étudiant de test
    Quand il se connecte, crée un ticket puis le consulte dans "Mes tickets"
    Alors le ticket apparaît au statut "Ouvert"

  Scénario: AC2 — Parcours admin
    Étant donné un admin de test
    Quand il passe le ticket à "En cours" avec une note
    Alors l'étudiant voit le nouveau statut

  Scénario: AC3 — Parcours chat vers ticket
    Étant donné un étudiant de test
    Quand il pose une question hors base de connaissances puis clique sur "Créer un ticket"
    Alors le formulaire est pré-rempli

  Scénario: AC4 — Accessibilité automatisée
    Étant donné les pages des parcours
    Quand un contrôle d'accessibilité automatisé s'exécute
    Alors aucune violation critique n'est remontée
```

## Exigences non fonctionnelles

- Le contrôle automatisé ne remplace pas une revue d'accessibilité manuelle avec technologies d'assistance.
- Le MFA admin est géré par un utilisateur de test dédié en dev (mécanisme à définir).

## Notes techniques / décisions

- Tests dans `tests/e2e`, exécutés après déploiement en dev.
