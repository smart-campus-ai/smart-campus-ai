## Contexte

La détection repose sur les services de sécurité au niveau compte. Dans le compte workshop, certains peuvent déjà être actifs : le module expose un interrupteur par service, positionné d'après le spike EN-11.

## User story

En tant qu'équipe OPS, je veux une baseline de sécurité activable service par service, afin de détecter les menaces et les écarts de conformité sans entrer en conflit avec l'existant.

## Critères d'acceptation

```gherkin
# language: fr
Fonctionnalité: EN-15 — Baseline sécurité

  Scénario: AC1 — Interrupteurs
    Étant donné les variables "enable_cloudtrail", "enable_guardduty", "enable_securityhub", "enable_config", "enable_access_analyzer"
    Quand l'une vaut false
    Alors le service correspondant n'est pas créé

  Scénario: AC2 — CloudTrail
    Étant donné "enable_cloudtrail" à true
    Quand le plan est calculé
    Alors un trail multi-régions avec validation des fichiers de log écrit dans un bucket privé, chiffré KMS, TLS-only

  Scénario: AC3 — Security Hub FSBP
    Étant donné "enable_securityhub" à true
    Quand le plan est calculé
    Alors le standard AWS Foundational Security Best Practices est activé

  Scénario: AC4 — GuardDuty, Config, Access Analyzer
    Étant donné les interrupteurs correspondants à true
    Quand le plan est calculé
    Alors un détecteur GuardDuty, un enregistreur Config et un analyseur IAM Access Analyzer sont créés
```

## Exigences non fonctionnelles

- Coût surveillé (Config et CloudTrail en particulier) via EN-16.

## Notes techniques / décisions

- Valeurs des interrupteurs par environnement dans les tfvars ; en compte partagé, une seule stack doit activer les services de niveau compte.
