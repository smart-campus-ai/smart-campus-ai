## Contexte

L'infrastructure possède la configuration, le pipeline applicatif possède le code (`ignore_changes` sur le code dans OpenTofu). Pour que OPS et SE avancent en parallèle sans se bloquer, l'interface entre les deux doit être écrite avant les modules et le code : variables d'environnement de chaque fonction, format des artefacts, mode de déploiement et contrat d'API.

## User story

En tant qu'équipes OPS et SE, nous voulons un contrat infra/app documenté et versionné, afin que chaque fonction soit déployable par le pipeline sans modification de l'infrastructure ni hypothèse implicite.

## Critères d'acceptation

```gherkin
# language: fr
Fonctionnalité: EN-05 — Contrat infra/app

  Scénario: AC1 — Variables d'environnement par fonction
    Étant donné le document de contrat
    Quand on cherche une fonction ("tickets", "kpi", "chat", "escalation", "notifier", "kb-sync", "kpi-aggregator", "pre-token")
    Alors on trouve la liste de ses variables d'environnement, leur signification et le module OpenTofu qui les fournit
    Et aucune variable ne contient de secret (seulement des noms de paramètres SSM ou de secrets lus à l'exécution)

  Scénario: AC2 — Format des artefacts Lambda
    Étant donné le document de contrat
    Quand SE prépare une fonction
    Alors le format attendu est explicite : une archive zip par fonction, construite pour arm64, avec le handler et le runtime déclarés

  Scénario: AC3 — Déploiement par alias
    Étant donné le document de contrat
    Quand on lit la section déploiement
    Alors il précise que chaque déploiement publie une version et bascule l'alias "live", que les intégrations pointent sur l'alias et que le rollback revient à la version précédente (EN-74)

  Scénario: AC4 — OpenAPI comme contrat d'API
    Étant donné "packages/contracts"
    Quand on l'ouvre
    Alors un document OpenAPI initial décrit les routes "/api/*", les schémas de requête réutilisés par la validation API Gateway (EN-33) et les codes 400/401/403/404
    Et sa validation (lint OpenAPI) fait partie de "task check"

  Scénario: AC5 — Évolution du contrat
    Étant donné une modification du contrat
    Quand une PR la propose
    Alors elle est relue par OPS et SE (CODEOWNERS) et référence les issues impactées
```

## Exigences non fonctionnelles

- Aucun secret, ARN de compte ni identifiant d'environnement codé en dur dans le contrat ; les valeurs proviennent des stacks (SSM `/smartcampus/<env>/<stack>/<key>`).
- Contrat versionné dans le dépôt ; toute rupture est signalée dans le titre de PR (Conventional Commits, `!`).

## Notes techniques / décisions

- Document proposé : `docs/architecture/infra-app-contract.md` ; schémas partagés dans `packages/contracts`.
- Le runtime est choisi par SE ; le contrat fixe seulement l'architecture arm64 et le format zip. Le mode de publication de l'artefact est fixé par EN-74.
- Les noms d'attributs des tables (`tickets`, `chat-sessions`, `kpi`) sont alignés ici (cf. EN-42, EN-53).
- Pas de VPC (architecture v3) : le contrat ne comporte aucun paramètre réseau.
