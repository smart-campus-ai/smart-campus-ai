## Contexte

L'architecture v3 impose des clés KMS gérées par le client, séparées par domaine (`data`, `logs`, `ai`), pour limiter le rayon d'impact et appliquer le moindre privilège à chaque service.

## User story

En tant qu'équipe OPS, je veux une clé KMS par domaine, afin de chiffrer chaque famille de données avec une politique d'accès dédiée.

## Critères d'acceptation

```gherkin
# language: fr
Fonctionnalité: EN-14 — Clés KMS par domaine

  Scénario: AC1 — Trois clés
    Étant donné la stack foundation
    Quand le plan est calculé
    Alors trois clés "data", "logs", "ai" existent avec un alias préfixé "sc-<env>"

  Scénario: AC2 — Rotation
    Étant donné chacune des clés
    Quand le plan est calculé
    Alors la rotation automatique est activée

  Scénario: AC3 — Politique explicite
    Étant donné la clé "logs"
    Quand on lit sa politique
    Alors le service CloudWatch Logs n'est autorisé qu'avec une condition sur le contexte de chiffrement ou "aws:SourceArn" / "aws:SourceAccount"
    Et aucun principal "*" n'est autorisé sans condition

  Scénario: AC4 — Publication pour la stack platform
    Étant donné les clés créées
    Quand l'apply se termine
    Alors leurs ARN sont publiés en SSM sous "/smartcampus/<env>/foundation/<key>"
```

## Exigences non fonctionnelles

- Fenêtre de suppression des clés en variable, valeur longue en prod.
