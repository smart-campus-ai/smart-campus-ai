## Contexte

Les administrateurs veulent suivre les tendances du support. Pour rester rapide et peu coûteux, les KPI sont lus depuis les agrégats journaliers de la table `kpi` (EN-46), maintenus à partir du stream des tickets, et non calculés par requête sur la table `tickets`.

## User story

En tant qu'administrateur, je veux accéder aux informations KPI sur les tickets, afin de suivre les tendances et d'identifier les goulets d'étranglement.

## Critères d'acceptation

```gherkin
# language: fr
Fonctionnalité: US05 — Consultation des KPI

  Scénario: AC1 — Indicateurs affichés
    Étant donné un admin authentifié
    Quand il ouvre le tableau de bord KPI
    Alors il voit le volume de tickets, le nombre de tickets ouverts, résolus et le temps moyen de résolution

  Scénario: AC2 — Filtres
    Étant donné le tableau de bord KPI
    Quand l'admin filtre par plage de dates, statut et catégorie
    Alors les indicateurs sont recalculés sur ce périmètre

  Scénario: AC3 — Tendances
    Étant donné une plage de dates
    Quand l'admin choisit la granularité jour, semaine ou mois
    Alors la tendance s'affiche à cette granularité
    Et les graphiques ont une alternative textuelle ou tabulaire accessible

  Scénario: AC4 — Lecture depuis les agrégats
    Étant donné une plage de N jours
    Quand l'API KPI répond
    Alors elle lit au plus O(N) éléments de la table "kpi"
    Et elle ne lit pas la table "tickets"

  Scénario: AC5 — Réservé aux administrateurs
    Étant donné un utilisateur du groupe "student"
    Quand il appelle l'API KPI
    Alors il reçoit une réponse 403
```

## Exigences non fonctionnelles

- Temps de réponse p95 < 2000 ms sur une plage d'un an (EN-84).
- Aucune donnée personnelle dans les agrégats.

## Notes techniques / décisions

- Fonction `kpi`, rôle IAM en lecture seule sur la table `kpi`.
- Temps moyen = somme des temps de résolution / nombre de tickets résolus, agrégés par jour, statut et catégorie.

## Dépendances

- EN-46 — Agrégats KPI
- EN-32 — Authorizer Cognito
- EN-33 — API REST
