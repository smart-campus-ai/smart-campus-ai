## Contexte

Cognito User Pool porte l'identité des étudiants et des administrateurs. La SPA utilise le flux authorization code + PKCE sans secret client. Les admins ont un MFA obligatoire. En dev, des utilisateurs de test permettent les tests automatisés et la démo.

## User story

En tant qu'équipe OPS, je veux un user pool Cognito configuré selon l'architecture v3, afin que la SPA authentifie les utilisateurs de façon sûre et que l'API reçoive des tokens fiables.

## Critères d'acceptation

```gherkin
# language: fr
Fonctionnalité: EN-31 — Cognito

  Scénario: AC1 — Groupes
    Étant donné le user pool
    Quand le plan est calculé
    Alors les groupes "student" et "admin" existent

  Scénario: AC2 — Client SPA PKCE
    Étant donné le client d'application
    Quand le plan est calculé
    Alors seul le flux "code" est autorisé, sans secret client
    Et les URL de callback et de déconnexion sont l'URL CloudFront de l'environnement

  Scénario: AC3 — Durée des tokens
    Étant donné le client d'application
    Quand le plan est calculé
    Alors la validité du token d'accès est de 60 minutes au plus
    Et la rotation des refresh tokens est activée

  Scénario: AC4 — MFA admin
    Étant donné un membre du groupe "admin"
    Quand il se connecte
    Alors un second facteur est exigé

  Scénario: AC5 — Protection contre les menaces
    Étant donné la fonctionnalité de protection contre les menaces disponible dans le compte
    Quand le plan est calculé
    Alors elle est activée derrière une variable

  Scénario: AC6 — Utilisateurs de test en dev uniquement
    Étant donné l'environnement "prod"
    Quand le plan est calculé
    Alors aucun utilisateur de test n'est créé
    Et en dev, les mots de passe des utilisateurs de test ne sont ni dans le code, ni dans les tfvars, ni dans les outputs
```

## Exigences non fonctionnelles

- Politique de mot de passe robuste ; e-mail comme identifiant.
- Les identifiants du pool et du client publiés en SSM pour la SPA et l'API.

## Notes techniques / décisions

- Mécanisme d'imposition du MFA admin (pool en MFA optionnel + contrôle, ou autre) à décider et consigner dans un ADR.
- Mots de passe de test générés et stockés en SSM SecureString ou Secrets Manager.
- Trigger `pre-token` et fédération Entra traités par US06.
