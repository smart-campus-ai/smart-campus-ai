## Contexte

**Pas de nom de domaine (décision du 22/10).** L'application est servie sur l'URL `*.cloudfront.net`. La redirection HTTPS est portée par EN-21. Le contournement de l'URL `execute-api` est couvert par le WAF régional de l'API REST (RF04). Le code reste prêt derrière `enable_custom_domain=false` (ACM en us-east-1, alias CloudFront, Route 53). Cette issue reste ouverte au statut « won't » pour la traçabilité.

## User story

En tant qu'équipe OPS, je veux que le domaine personnalisé et son certificat ACM soient activables par un simple flag, afin de pouvoir passer sur le domaine officiel le jour où il sera disponible.

## Critères d'acceptation

```gherkin
# language: fr
Fonctionnalité: EN-22 — Domaine personnalisé (won't)

  Scénario: AC1 — Désactivé par défaut
    Étant donné "enable_custom_domain" à false
    Quand le plan est calculé
    Alors aucun certificat ACM, aucun enregistrement Route 53 et aucun alias CloudFront n'est créé

  Scénario: AC2 — Activable sans refonte
    Étant donné "enable_custom_domain" à true et un nom de domaine fourni
    Quand le plan est calculé avec le provider simulé
    Alors un certificat ACM est prévu en us-east-1 avec validation DNS et renouvellement géré
    Et la distribution déclare l'alias et le certificat

  Scénario: AC3 — Validation des variables
    Étant donné "enable_custom_domain" à true sans nom de domaine
    Quand le plan est calculé
    Alors la validation échoue avec un message explicite
```

## Exigences non fonctionnelles

- Aucun coût tant que le flag est à false.

## Notes techniques / décisions

- Décision documentée dans l'ADR « pas de domaine » (EN-91).
- Ne pas planifier dans un sprint ; réouvrir la priorisation si un domaine devient disponible.
