## Contexte

Un scan dynamique de base (OWASP ZAP baseline) détecte les faiblesses courantes du front et de l'API déployés. Il tourne chaque nuit, uniquement sur dev.

## User story

En tant que QE, je veux un scan DAST nocturne sur dev, afin de repérer les vulnérabilités web avant qu'elles n'atteignent la prod.

## Critères d'acceptation

```gherkin
# language: fr
Fonctionnalité: EN-86 — DAST ZAP baseline

  Scénario: AC1 — Exécution planifiée
    Étant donné le workflow DAST
    Quand il s'exécute chaque nuit
    Alors un scan ZAP baseline cible l'URL CloudFront de dev uniquement

  Scénario: AC2 — Rapport
    Étant donné un scan terminé
    Quand on consulte l'exécution
    Alors le rapport est disponible en artefact

  Scénario: AC3 — Alerte
    Étant donné une alerte de risque élevé
    Quand le scan se termine
    Alors une issue labellisée "security" est créée ou mise à jour

  Scénario: AC4 — Faux positifs tracés
    Étant donné une règle ignorée
    Quand on lit la configuration
    Alors chaque exclusion porte une justification
```

## Exigences non fonctionnelles

- Pas de scan sur prod ; volume compatible avec le WAF (liste d'autorisation ou seuils dev à prévoir).

## Notes techniques / décisions

- Le WAF peut bloquer le scanner : stratégie à décider (scan authentifié, exclusion temporaire documentée).

## Dépendances

- EN-81 — Stratégie de test

- [ ] Workflow planifié, permissions minimales, zizmor et actionlint sans finding
- [ ] Premier rapport analysé et joint à l'issue
