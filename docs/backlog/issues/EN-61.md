## Contexte

L'équipe technique doit identifier rapidement les incidents de production. Cette issue centralise les logs (Lambda, API Gateway, WAF), les traces, un tableau de bord et les alarmes vers SNS. Les critères du doublon fermé #17 y sont fusionnés : tableaux de bord, erreurs d'authentification, 5xx, latence.

## User story

En tant qu'équipe OPS, je veux centraliser les logs et configurer des alertes d'erreurs, afin d'identifier rapidement les incidents de production.

## Critères d'acceptation

```gherkin
# language: fr
Fonctionnalité: EN-61 — Logs, dashboards et alertes

  Scénario: AC1 — Logs centralisés
    Étant donné les fonctions Lambda, le stage de l'API REST et les web ACL
    Quand le plan est calculé
    Alors chacun écrit dans un groupe CloudWatch Logs explicite, chiffré par la clé "logs", avec rétention (dev 14 j, prod 90 j)
    Et les logs applicatifs et d'accès sont en JSON structuré

  Scénario: AC2 — Traces
    Étant donné une requête traversant l'API et une Lambda
    Quand on consulte X-Ray
    Alors la trace relie l'API Gateway et la fonction

  Scénario: AC3 — Tableau de bord
    Étant donné un environnement déployé
    Quand on ouvre le tableau de bord CloudWatch
    Alors il présente requêtes, 4xx/5xx, latence p95, erreurs et throttles Lambda, profondeur des DLQ, blocages WAF

  Scénario: AC4 — Erreurs d'authentification visibles
    Étant donné des réponses 401/403 de l'API
    Quand on consulte les logs et le tableau de bord
    Alors elles sont exploitables (filtre de métrique dédié) et une alarme se déclenche sur un pic

  Scénario: AC5 — Alarmes vers SNS
    Étant donné les seuils configurés
    Quand le taux de 5xx, la latence p95, les throttles, la profondeur d'une DLQ, les blocages WAF ou les erreurs Lambda dépassent leur seuil
    Alors une notification est publiée sur le topic SNS ops

  Scénario: AC6 — Pas de PII dans les logs
    Étant donné les logs d'accès de l'API
    Quand on inspecte leur format
    Alors ils ne contiennent ni en-tête "Authorization", ni corps de requête
```

## Exigences non fonctionnelles

- Seuils en variables avec valeurs dev/prod.
- Coût maîtrisé : pas de logs de debug en prod par défaut.

## Notes techniques / décisions

- Module `observability` dans `stacks/foundation` ou `stacks/platform` selon les ressources observées ; il reçoit les noms à surveiller en entrée (pas de découverte).
- Topic SNS ops fourni par EN-45.
