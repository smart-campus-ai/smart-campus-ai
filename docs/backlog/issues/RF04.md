## Contexte

L'application doit être protégée contre les attaques et les abus d'inférence. Sans nom de domaine, l'URL `execute-api` de l'API REST ne peut pas être désactivée : la protection placée uniquement sur CloudFront serait contournable. Il faut donc **deux web ACL** : l'une sur CloudFront (scope CLOUDFRONT, us-east-1), l'autre régionale sur le stage de l'API REST. La seconde porte les règles de débit, agrégées sur l'en-tête `Authorization` (par utilisateur) et par IP.

## User story

En tant qu'architecte sécurité, je veux protéger le front et l'API REST avec AWS WAF et une limitation de débit, afin de prémunir l'application contre les attaques et les abus d'inférence.

## Critères d'acceptation

```gherkin
# language: fr
Fonctionnalité: RF04 — WAF et limitation de débit

  Scénario: AC1 — Web ACL CloudFront
    Étant donné la distribution CloudFront
    Quand le plan est calculé
    Alors une web ACL de scope CLOUDFRONT (us-east-1) est attachée à la distribution
    Et elle contient les groupes gérés Common, KnownBadInputs, IpReputation, AnonymousIp et une limite de taille du corps

  Scénario: AC2 — Web ACL régionale sur l'API REST
    Étant donné le stage de l'API REST
    Quand le plan est calculé
    Alors une web ACL REGIONAL est associée au stage avec les mêmes groupes gérés et la limite de taille du corps

  Scénario: AC3 — Débit par utilisateur
    Étant donné la web ACL régionale
    Quand un même en-tête "Authorization" dépasse le seuil de requêtes sur la fenêtre
    Alors les requêtes suivantes sont bloquées

  Scénario: AC4 — Débit par IP
    Étant donné la web ACL régionale
    Quand une même IP dépasse le seuil de requêtes sur la fenêtre
    Alors les requêtes suivantes sont bloquées

  Scénario: AC5 — Pas de contournement par execute-api
    Étant donné un client qui appelle directement l'URL "execute-api"
    Quand il dépasse le seuil de débit
    Alors il est bloqué comme s'il passait par CloudFront

  Scénario: AC6 — Requête malveillante filtrée
    Étant donné une requête contenant une charge reconnue par les groupes gérés
    Quand elle atteint CloudFront ou l'API
    Alors elle est bloquée (403)

  Scénario: AC7 — Journalisation
    Étant donné les deux web ACL
    Quand une requête est évaluée
    Alors les logs sont écrits dans un groupe CloudWatch "aws-waf-logs-*" chiffré KMS avec rétention définie
```

## Exigences non fonctionnelles

- Seuils de débit en variables, validés (> 0), avec valeurs dev/prod dans les tfvars.
- Le contenu de l'en-tête `Authorization` est masqué dans les logs WAF (redacted fields).

## Notes techniques / décisions

- Le throttling par stage et par méthode d'API Gateway complète le WAF ; il est porté par EN-33 et vérifié ici.
- Blocages WAF alarmés par EN-61 ; tests de débit dans EN-83.
- Provider alias `aws.us_east_1` pour l'ACL CloudFront.
