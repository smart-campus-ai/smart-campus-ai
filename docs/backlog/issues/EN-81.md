## Contexte

La Definition of Done impose que chaque critère d'acceptation soit couvert par un test automatisé nommé d'après lui (`US04-AC2 …`). Il faut une stratégie commune (niveaux de test, outils, environnements) et une matrice qui relie chaque AC à ses tests.

## User story

En tant que QE, je veux une stratégie de test et une matrice de traçabilité, afin de prouver que chaque exigence est vérifiée et de repérer les trous de couverture.

## Critères d'acceptation

```gherkin
# language: fr
Fonctionnalité: EN-81 — Stratégie de test

  Scénario: AC1 — Stratégie publiée
    Étant donné "docs/qa/"
    Quand on consulte la stratégie
    Alors elle décrit les niveaux (unitaire IaC, unitaire applicatif, smoke, sécurité, performance, E2E, DAST), les outils, les environnements et les déclencheurs

  Scénario: AC2 — Convention de nommage
    Étant donné un test automatisé
    Quand on lit son nom
    Alors il commence par l'identifiant de l'AC qu'il couvre ("<ID>-ACn")

  Scénario: AC3 — Matrice générée
    Étant donné les issues et les tests du dépôt
    Quand la matrice est produite
    Alors chaque AC des issues "must" apparaît avec ses tests ou est marqué "non couvert"

  Scénario: AC4 — Critères de sortie
    Étant donné la stratégie
    Quand on cherche les critères de promotion dev → prod
    Alors ils sont explicites (tests requis, seuils de performance, zéro finding critique)
```

## Exigences non fonctionnelles

- La matrice est régénérable automatiquement (script ou tâche), pas maintenue à la main.

## Notes techniques / décisions

- Données de test : jamais de données personnelles réelles.

## Dépendances

- Aucune

## Definition of Done

- [ ] Stratégie et matrice publiées dans `docs/qa/` et relues par l'équipe
- [ ] Tâche de génération de la matrice documentée
- [ ] Issue mise à jour avec une note d'avancement
