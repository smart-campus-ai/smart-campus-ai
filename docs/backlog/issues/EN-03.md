## Contexte

Les dépendances (actions GitHub, providers, outils) sont une surface d'attaque. Elles doivent être épinglées et tenues à jour automatiquement, et les secrets bloqués avant d'atteindre le dépôt.

## User story

En tant qu'équipe OPS, je veux sécuriser la chaîne d'approvisionnement du dépôt, afin d'éviter l'introduction de dépendances compromises ou de secrets.

## Critères d'acceptation

```gherkin
# language: fr
Fonctionnalité: EN-03 — Chaîne d'approvisionnement

  Scénario: AC1 — Actions épinglées par SHA
    Étant donné les workflows et actions composites
    Quand le linter de workflows s'exécute
    Alors toute action tierce est référencée par un SHA de commit complet

  Scénario: AC2 — Mises à jour automatiques
    Étant donné Renovate configuré
    Quand une nouvelle version d'une action, d'un provider ou d'un outil de ".mise.toml" est publiée
    Alors une PR de mise à jour conventionnelle (scope "deps") est ouverte vers "develop"

  Scénario: AC3 — Secret scanning et push protection
    Étant donné les paramètres de sécurité du dépôt
    Quand on pousse un commit contenant un secret détectable
    Alors le push est bloqué

  Scénario: AC4 — Scan des secrets en CI
    Étant donné une PR
    Quand la CI s'exécute
    Alors gitleaks analyse les changements et échoue en cas de secret
```

## Exigences non fonctionnelles

- Les PR Renovate passent par les mêmes checks que les autres PR.

## Notes techniques / décisions

- Le lock file `.terraform.lock.hcl` est régénéré avec les hashes multi-plateformes à chaque mise à jour de provider.
